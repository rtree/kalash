# KALASH implementation design

## 1. Current scope and execution hosts

M1 first vertical slice: `/temples/temple-01` -> 0.01 test USDC ->
Central receipt verification -> real stamp -> Collection reload.
This document defines intended contracts; TASKS records verification, not this file.

| Responsibility | Host | Address / status |
|---|---|---|
| Web/API development | Current Windows ARM64, Node 26.13.0 | `http://localhost:3000` (not started) |
| Contract compile / isolated chain tests | Windows solc compile; Cloud Build Linux for chain tests | Ganache native leveldown incompatible with Windows ARM64; browser fallback also failed; no further Windows framework retries |
| Cloud build / production | GCP Cloud Build / Cloud Run | `kalash-donation`, `asia-south1`; HTTPS URL not yet assigned |
| Controller / ITL | Current Windows ARM64, .NET 10 | ITL loopback `http://localhost:5000`; no device operations authorized yet |
| Android | Current Windows host, USB-connected authorized Samsung | ADB37.0.1 at `%LOCALAPPDATA%\KALASH\tools\platform-tools-37.0.1\platform-tools\adb.exe`; use exact serial. Phone URL will use reverse only for this host |

User confirms nested virtualization is unavailable; use Cloud Build rather than Docker/WSL.
Central is one process serving React, API and a durable mint loop.
Firebase Auth verifies identity, Firestore is the only application writer's store,
Secret Manager supplies minter key, private Storage is reserved for M2.
Browser -> same-origin Central -> Auth/Firestore/Base RPC.
Windows Controller -> outbound Central HTTPS; never expose ITL.

## 2. M1 identifiers, units and states

Chain 84532 only. Circle USDC `0x036CbD53842c5426634e7929541eC2318f3dCF7e`,
6 decimals; verify RPC chain, token bytecode and decimals before sending.
`templeId`: stable `temple-01` through `temple-10`.
`donationId`: server-generated bytes32, bound to verified wallet before submission.
API monetary values are canonical unsigned decimal strings. No floating-point money.
`0 < amount <= 1000000`, default `10000`; fee = amount / 10000 (integer floor).
Default fee `1`, temple net `9999`. Point units: USDC units times multiplier;
10000 point units = 1 point. Remote multiplier 1; onsite multiplier 10.
Browser cannot assign onsite kind or recipient.

Donation: intent -> submitting -> unknown/submitted -> confirmed or failed/expired.
Missing receipt or hash means unknown/pending, never safe to resend.
Mint: reserved -> prepared (signed bytes/hash persisted) -> submitted -> minted;
errors remain explicit and retryable only by the same persisted transaction.
Expiry forbids new execution; a matching timely chain transaction can still settle.

## 3. Authentication and API contract

SIWE challenge binds domain, origin, chain 84532, one-time nonce and expiry.
Central verifies signature then issues Firebase custom token. API requires Firebase
ID token and server-verified wallet claim. Never authenticate using public txHash.
Wallet change invalidates prior client identity. No browser Firestore writes.

Planned same-origin endpoints:
- `GET /api/temples`: public demo temple catalog and deployment configuration.
- `POST /api/auth/challenge`: wallet -> nonce and exact sign-in message.
- `POST /api/auth/verify`: nonce/message/signature -> Firebase custom token.
- `POST /api/donations`: authenticated templeId/amount -> immutable intent.
- `POST /api/donations/:id/operation`: persist operation, source, chain and start block.
- `POST /api/donations/:id/verify`: optional txHash hint, owner only; await verification.
- `GET /api/donations/:id`, `GET /api/collection`, `GET /api/history`: owner only.

Confirm canonical successful receipt, target, sender, calldata, chain and exact
Donated event. Key chain/tx/log deterministically. Transactionally store donation,
point increment and mint reservation once. Collection counts successful mints,
deduplicated by donationId, grouped wallet/temple/kind; pending displayed separately.
Event scan by donationId recovers missing hash without automatic donation resubmission.

## 4. Contracts and persistence

Solidity responsibilities: DonationVault, CashFeeVault, nontransferable ERC-1155 Stamp.
DonationVault stores registered temple destinations and consumes donationId once.
Intent authorization must bind sender/temple/amount/kind/expiry/chain/vault.
`Donated(bytes32 donationId, address donor, bytes32 templeId, uint8 kind,
uint256 amount, uint256 fee, address recipient)`.
Stamp consumes donationId once; metadata exposes temple, kind and date only.
Actual ABI/bytecode: `config/contracts.abi.json`; deployments and receipt hashes:
`config/deployment.public.json`. Compiled Solidity0.8.38, Shanghai. Cloud Build Linux
23 isolated chain assertions passed (build ID in TASKS); Windows compiles using JS.
DonationVault `0x7a5b5ccc5410e1c9ad4fef8f40bf9786cb842073`,
KalashStamp `0x853d271ed9461f4e56c449d8c2b7c83b410b4cbb`.

EIP712 domain `KALASH Donation`, version `1`, chainId84532, verifyingContract=vault.
`Donation(bytes32 donationId,address donor,bytes32 templeId,uint8 kind,uint256 amount,uint256 deadline)`.
Temple key is keccak256(UTF8 templeId); remote kind0, onsite kind1.
`donate(bytes32,bytes32,uint8,uint256,uint256,bytes)` consumes server-signed intent.
Stamp `mint(bytes32,address,bytes32,uint8,uint256)` uses UTC epoch day; tokenId is
uint256(donationId), amount1. `StampMinted(bytes32 indexed donationId,address indexed
recipient,uint256 indexed tokenId,bytes32 templeId,uint8 kind,uint256 day)` plus TransferSingle.

Firestore deterministic records: challenges, donations, chainEvents,
walletTempleTotals, mintJobs, processLeases, temples.
Mint loop approximately 1s, one nonce owner via database lease; no independent worker.
Do not run local and cloud loops concurrently against the same minter/DB.
Minter key is read from Secret Manager `kalash-minter-key` using ADC. Reown project ID
is read from `kalash-reown-project-id` (client-visible by design, not an auth secret).
Runtime SA `kalash-central@kalash-donation.iam.gserviceaccount.com` has Firestore user,
Firebase Auth admin, quota use, per-secret accessor and self custom-token signing.
Local ADC and CLI identity differed; scoped runtime signBlob access was explicitly
granted to ADC principal and verified by actual Firebase createCustomToken.
Firestore point increments and mint reservation share one transaction.
Prepared mint stores raw signed transaction/hash/nonce BEFORE broadcast.
Original cumulative gas budget .003 ETH, mint count20, persisted transactionally;
excess wallet balance does not expand budget. Deployment budget .01 ETH likewise persists.

## 5. Dependency and validation entry

Pinned Node 26.13.0 (Lithium LTS), pnpm 10.34.9.
`node scripts/check-policy.mjs` precedes acquisition and every validation entry.
First install only: `pnpm install --ignore-scripts`; then verify publication timestamps
and lock hash before executing dependency code. Thereafter frozen lockfile only.
Release verification report includes UTC reference, all locked versions/timestamps,
verdict, policy fingerprint and SHA-256 lockfile hash. No age exclusions or hooks.
