## 1. Current scope and execution hosts

## 2. M1 identifiers, units and states

Chain 84532 only. Circle USDC `0x036CbD53842c5426634e7929541eC2318f3dCF7e`,
6 decimals; verify RPC chain, token bytecode and decimals before sending.
`templeId`: stable `temple-01` through `temple-10`.
`donationId`: server-generated bytes32, bound to verified wallet before submission.
API monetary values are canonical unsigned decimal strings. No floating-point money.
Only donation creation accepts decimal USDC input. Donation responses already
contain base units: wallet approval/calldata use parseDonationUnits, never the
decimal-input parseAmount; history/pending displays format those units directly.
`0 < amount <= 1000000`, default `10000`; fee = amount / 10000 (integer floor).
Default fee `1`, temple net `9999`. Point units: USDC units times multiplier;
10000 point units = 1 point. Remote multiplier 1; onsite multiplier 10.
Browser cannot assign onsite kind or recipient.

The above intent cap and 1 bps fee apply to Crypto only. Cash is a distinct
`paymentMethod: cash` record: INR paise, converted units = paise * 100,
onsite kind 1, `chainId`/`txHash` null, and a 3% temple fee marked unpaid.
It has no Vault signature, approval, or payment receipt. Crypto operation,
approval recovery and receipt endpoints reject cash records. Donor cash status
and mint polling use the authenticated donation GET instead; mint remains a
separate transaction. Cash history/progress displays INR, physical reconciliation
and the temple's unpaid fee, never a fabricated token payment.

Donation: intent -> submitting -> unknown/submitted -> confirmed or failed/expired.
Missing receipt or hash means unknown/pending, never safe to resend.
Mint: reserved -> prepared (signed bytes/hash persisted) -> submitted -> minted;
errors remain explicit and retryable only by the same persisted transaction.
Expiry forbids new execution; a matching timely chain transaction can still settle.
An approval-only intent may leave a client-side pending operation. Do not silently
clear it or retry approval. An owner-only recovery endpoint may abandon an active
or expired approval-only flow only when its registered operations are approval-only,
no `donateAttemptId` or `txHash` exists, no USDC `Approval` or Vault `Donated` event
was found from `startBlock` through the current canonical head, and current Vault
USDC allowance is zero. Scan logs in RPC-compatible 200-block chunks and reject
requests requiring more than 20,000 blocks. If the head is already past the intent
deadline, binary-search the last deadline-valid block and scan only through it;
otherwise scan through the head. Preserve the operation history and resolution
block/allowance evidence. If the signature deadline has not passed, mark the local
flow `cancelled`, not `expired`: the signed authorization is not revoked on-chain
and remains valid until its deadline. Warn the owner not to submit that old intent
manually. The UI must require explicit confirmation that no wallet request is open.
This path never signs, approves, donates, refunds, or deletes the record.
An early-cancelled signed intent remains valid until its deadline; `createDonation`
must reject a new intent for that wallet while any such cancelled signature remains
valid. After expiry, the guard clears automatically.

The normal approval sequence is to persist the donation intent and approve operation,
then call the connected wallet provider to request the exact USDC approval. MetaMask
must display that request before any approval receipt can be checked; the Central
recovery action is not an approval substitute and never opens MetaMask.
A wallet write can fail while Viem prepares fees/gas, before the wallet modal appears.
For example, `Custom eth_getBlockByNumber: Unauthorized` is a wallet/provider RPC
failure, not an approval or donation result. The browser's public allowance RPC and
the wallet provider may use different RPC backends; do not infer that the wallet
endpoint is healthy from the browser read, force gas values, or retry blindly.
Keep the exact error and sanitized provider trace, and verify the wallet's chain/RPC
configuration before making another approval attempt.
For WalletConnect's Blockchain RPC HTTP API, `/v1` requires both a CAIP-2
`chainId` and a `projectId` query parameter; a bare `rpc.walletconnect.org/v1`
hostname is not a complete request URL. Do not copy credential-bearing RPC URLs
into logs or ask the owner to share the project ID. See the [WalletConnect Blockchain
RPC specification](https://specs.walletconnect.com/2.0/specs/servers/blockchain/blockchain-rpc-api).

## 3. Authentication and API contract

SIWE challenge binds domain, origin, chain 84532, one-time nonce and expiry.
Central verifies signature then issues Firebase custom token. API requires Firebase
ID token and server-verified wallet claim. Never authenticate using public txHash.
Wallet change invalidates prior client identity. No browser Firestore writes.

Planned same-origin endpoints:
- `GET /api/temples`: public demo temple catalog and deployment configuration.
- `POST /api/auth/challenge`: wallet -> nonce and exact sign-in message.
- `POST /api/auth/verify`: nonce/message/signature -> Firebase custom token.
- `POST /api/donations`: authenticated templeId/amount -> immutable intent.
- `POST /api/donations/:id/operation`: persist operation, source, chain and start block.
- `POST /api/donations/:id/verify`: optional txHash hint, owner only; await verification.
- `POST /api/donations/:id/resolve-approval`: owner-only, proof-checked abandonment of an approval-only flow; never a payment retry.
- `GET /api/donations/:id`, `GET /api/collection`, `GET /api/history`: owner only.

For owner-only `GET /api/history`, Central may include `approvalAttemptId` only for
an active intent with no donation submission and exactly one registered approve
operation matching the owner, Base Sepolia, USDC, and immutable amount. History uses
this to restore the abandonment control when local browser state is lost; it does
not expose an approval action or submit a transaction.

Confirm a canonical successful receipt on chain 84532 and the exact immutable
DonationVault `Donated` event. For direct EOA transactions also require the expected
sender, vault target and exact signed calldata. For delegated/account-abstraction
transactions, the outer sender and target are not the donor or vault: require the
receipt's exact donor/intent event plus the configured USDC contract's complete set
of donor-originating transfers, matching the vault's on-chain fee recipient and the
intent's fee/net destinations and amounts. Reject extra or mismatched donor transfers;
never accept an outer sender, transaction target, event, or user-supplied hash alone.
Key chain/tx/log deterministically. Transactionally store donation, point increment
and mint reservation once. Collection counts successful mints, deduplicated by
donationId, grouped wallet/temple/kind; pending displayed separately. Event scan by
donationId recovers missing hash without automatic donation resubmission.

## 4. Contracts and persistence

Solidity responsibilities: DonationVault, CashFeeVault, nontransferable ERC-1155 Stamp.
DonationVault stores registered temple destinations and consumes donationId once.
Intent authorization must bind sender/temple/amount/kind/expiry/chain/vault.
`Donated(bytes32 donationId, address donor, bytes32 templeId, uint8 kind,
uint256 amount, uint256 fee, address recipient)`.
Stamp consumes donationId once; metadata exposes temple, kind and date only.
Actual ABI/bytecode: `config/contracts.abi.json`; deployments and receipt hashes:
`config/deployment.public.json`. Compiled Solidity0.8.38, Shanghai. Cloud Build Linux
23 isolated chain assertions passed (build ID in TASKS); Windows compiles using JS.
DonationVault `0x7a5b5ccc5410e1c9ad4fef8f40bf9786cb842073`,
KalashStamp `0x853d271ed9461f4e56c449d8c2b7c83b410b4cbb`.

EIP712 domain `KALASH Donation`, version `1`, chainId84532, verifyingContract=vault.
`Donation(bytes32 donationId,address donor,bytes32 templeId,uint8 kind,uint256 amount,uint256 deadline)`.
Temple key is keccak256(UTF8 templeId); remote kind0, onsite kind1.
`donate(bytes32,bytes32,uint8,uint256,uint256,bytes)` consumes server-signed intent.
Stamp `mint(bytes32,address,bytes32,uint8,uint256)` uses UTC epoch day; tokenId is
uint256(donationId), amount1. `StampMinted(bytes32 indexed donationId,address indexed
recipient,uint256 indexed tokenId,bytes32 templeId,uint8 kind,uint256 day)` plus TransferSingle.

Firestore deterministic records: challenges, donations, chainEvents,
walletTempleTotals, mintJobs, processLeases, temples.
Mint loop approximately 1s, one nonce owner via database lease; no independent worker.
Do not run local and cloud loops concurrently against the same minter/DB.
Minter key is read from Secret Manager `kalash-minter-key` using ADC. Reown project ID
is read from `kalash-reown-project-id` (client-visible by design, not an auth secret).
Runtime SA `kalash-central@kalash-donation.iam.gserviceaccount.com` has Firestore user,
Firebase Auth admin, quota use, per-secret accessor and self custom-token signing.
Local ADC and CLI identity differed; scoped runtime signBlob access was explicitly
granted to ADC principal and verified by actual Firebase createCustomToken.
Firestore point increments and mint reservation share one transaction.
Prepared mint stores raw signed transaction/hash/nonce BEFORE broadcast.
Original cumulative gas budget .003 ETH, mint count20, persisted transactionally;
excess wallet balance does not expand budget. Deployment budget .01 ETH likewise persists.

## 5. Dependency and validation entry

Policy fingerprints normalize CRLF to LF for the four policy input files so
Windows checkouts and committed-source Linux archives produce identical evidence.
The lockfile SHA remains byte-exact; versions, effective settings and the
168-hour release checks are unchanged. The policy test rejects real content
changes and incorrect Node versions on either host.
For a committed-source Cloud Build upload on Windows use
`git -c core.autocrlf=false archive --format=tar.gz` so the archive preserves
the lockfile's committed bytes. Verify the archive's lock SHA and policy
fingerprint against its embedded release evidence before upload; never bypass
the check or include unrelated dirty worktree content.

Pinned Node 26.13.0 (Lithium LTS), pnpm 10.34.9.
`node scripts/check-policy.mjs` precedes acquisition and every validation entry.
First install only: `pnpm install --ignore-scripts`; then verify publication timestamps
and lock hash before executing dependency code. Thereafter frozen lockfile only.
Release verification report includes UTC reference, all locked versions/timestamps,
verdict, policy fingerprint and SHA-256 lockfile hash. No age exclusions or hooks.

## 6. M2 photos and public boards

Photos are never uploaded automatically after donation. An authenticated owner must
select a confirmed donation, preview a JPEG/PNG/WebP locally, and explicitly consent
before Central accepts the upload. Central decodes the bytes with a 20 MP pixel limit,
rejects animation and unsupported formats, applies EXIF orientation, and re-encodes
to metadata-free JPEG (1600px maximum dimension, 5 MB input / 3 MB output limits).
Display-name text is optional, normalized and length-limited.

“Take a photo” opens `getUserMedia({video:true,audio:false})` directly instead of
relying on the optional HTML file-input `capture` hint. Use default camera constraints,
show an in-page preview and capture into a local JPEG. Never upload on capture. Stop
all media tracks on capture, close, component unmount or route change. Permission
denial, missing camera or unsupported secure context must remain visible and leave
the image chooser/skip route available.

Store objects in private `kalash-donation-photos` (asia-south1), uniform bucket-level
access, public-access prevention, no soft-delete retention. The Cloud Run runtime
service account has bucket-scoped objectAdmin for application reads/writes; project
administrators retain control-plane access. No public grants are configured. Never
return storage paths or signed GCS URLs.
The public board API exposes only photo ID, temple, optional display name, size tier,
creation/expiry and a same-origin image route. That route rechecks the published photo
and current owner/temple slot on every request and returns `no-store`; replacing,
withdrawing or expiring a photo blocks public delivery before attempting object
deletion. Failed deletions are queued durably for retry.

One latest photo per verified wallet/temple slot; each published image expires after
30 days. Firestore records keep donation/owner/consent/points private. Public DTOs must
never include those fields. `photoSizeTier` uses integer point units and shared
thresholds: 1–499, 500–1,999, 2,000–4,999 and 5,000+ points; zero is ineligible.
An expiry queue and cleanup queue are processed by the existing Central process.
The owner may withdraw; operator/temple withdrawal authorization remains to be added.
Withdrawal follow-up is deferred, not removed from the final acceptance criteria.
Remote and onsite crypto use phone photos; cash donations use ATM photos.

API: `GET /api/photos/eligibility/:donationId`, `POST /api/photos`,
`GET /api/photos/mine`, owner-only `POST /api/photos/:id/withdraw`,
public `GET /api/board/:templeId/photos` and same-origin image delivery at
`GET /api/board/:templeId/photos/:id`. Public board and direct image requests do not
use Firebase auth or GCS public access; every image request rechecks published state.
Pilgrim entry points are confirmed-donation History, Collection → Photos and each
temple detail’s “View community photo board” link. Post-publication links go directly
to the relevant temple board.

M3 cash controller/reconciliation, M4 fee/payout, and M5 onsite crypto remain required;
their implementation is not implied by M1 code.

## 8. ATM reception milestones: disconnected Crypto first, Cash next

Only the registered `temple-01` ATM supports onsite reception. Other temples remain
remote-only. A verified USB disconnect is a supported state: onsite Crypto can
proceed while Cash is visibly disabled. Unknown, stale or absent Controller/device
health also fails closed for Cash; it must never block the Crypto option.

### 8.1 M5a onsite Crypto while the cash machine is disconnected

ATM screen: Crypto -> Central reception QR -> phone MetaMask opens the same
temple detail -> connect/SIWE if needed -> explicit Join -> amount/approve/donate
on the phone -> Central verifies success receipt and immutable `Donated` event ->
ATM returns to idle. The ATM does not wait for mint or photos. The phone retains
its donation result and can visit Collection or share an optional photo.

An onsite Crypto intent is `kind=1`, bound to the claimed `visitSessionId`,
verified wallet and registered temple; no query flag or caller-supplied kind can
set it. Donation receipt matching, operation registration, mint reservation,
Collection deduplication and points reuse M1. Onsite crypto points use multiplier
10. The normal Pilgrim `POST /api/donations` remains `kind=0`; only the
authenticated, claimed visit endpoint may create `kind=1`.

The QR reference is for discovery, not payment authority. QR view never claims
the visit. SIWE identifies the wallet, but a separate explicit Join action binds
that wallet to this one visit. Claim is atomic/idempotent; another wallet,
temple, ATM, expired visit or replay is rejected. Public visit responses contain
no owner wallet, donation hash or device credential.

Central/ATM state is polled every 2 seconds and restored after browser visibility
or reload. After the donation has a canonically verified `confirmed` state, the
ATM clears only that active visit and returns to idle. `unknown`, `submitting`,
`submitted` or other unresolved outcomes keep the ATM occupied and reuse the
same donation ID. Failed/expired outcomes require explicit recovery; timers and
screen refreshes never synthesize success or resubmit.

The successful receipt-only slice must report Cash disabled when the Controller
heartbeat is absent/stale or ITL reports no attached USB device. During M5a,
Cash remains unavailable even if a controller is present: the cash workflow is
the next M3 goal, not a feature flag in this release.

### 8.2 M3 onsite cash (next goal after M5a)

Central owns `visitSessionId`, `atmId`, `templeId`, purpose (`cash`/`crypto`), expiry,
state, verified owner and the eventual `cashSessionId`/`donationId`. A random public
reference in the QR is for discovery, not a bearer grant. Viewing it never claims
it. Claim is an explicit authenticated action, atomic and idempotent for the same
owner; concurrent/foreign owners, wrong ATM/temple and expired references are
rejected. Cash also requires a one-use wallet signature binding origin, chain,
temple, ATM, visit/cash session, purpose, nonce and expiry. Normal login alone is
not consent to a new cash reception.

Controller authenticates to Central using an ATM-bound credential stored outside
Git. A short-lived, single-use screen pairing code authorizes the Donate Screen;
knowing `/atm/:atmId` is not authorization. Screen and Controller grants are
separate. No wallet session, Firebase ID token, device credential or photo grant
is placed in a deeplink. Sensitive responses are `no-store`.

The QR encodes `https://link.metamask.io/dapp/<canonical-host>/temples/<templeId>?visit=<reference>`.
Only the configured HTTPS origin, known temple route and exact visit parameter
are accepted; preserve escaped path/query without encoding the whole target.
The screen also displays temple, purpose, destination and remaining QR lifetime.
The phone resolves the reference, presents the context, then connects/verifies
and explicitly joins. ATM and phone poll authorized Central state every 2 seconds
while active, refresh on visibility return, and stop on departure. No direct
phone-to-ATM connection is needed.

Initial independent time limits: unclaimed QR 120 seconds; cash acceptance 120
seconds measured from actual Controller Ready; ATM photo inactivity 30 seconds.
One unresolved reception per ATM is enforced transactionally. A QR timeout may
close an unclaimed reception, but never cancels an in-flight cash/payment action.

Cash: awaiting claim -> awaiting device -> accepting -> closing -> confirmed or
reconciling. Done, receipt deadline and capacity stop new acceptance first.
Only authenticated, ordered Controller STORED events, note keys, counters and
denomination-level inventory reconciliation can confirm cash. Zero stored cash
closes without donation/mint/photo. Unknown results keep the ATM locked.
No browser action or development timer can synthesize Ready, stored cash or
confirmation. ITL commands remain disabled until device authentication, exclusive
poller ownership, routing/inventory and owner attendance have been established.
Use SPEC section 8 for durable commands/events and no-blind-retry semantics.
After the one-use signed consent transaction, Central stores a deterministic
pending `start_cash` command with the visit/session binding. The authenticated
Controller can retrieve that same command from
`GET /api/controller/:atmId/commands`; repeated reads do not mark it executed or
enable acceptance. Controller-side persistence, preflight, execution and result
reporting remain required before the ATM may show acceptance as active.
Central accepts ordered idempotent command-state reports and changes the visit
to `accepting` only after a Controller `observed` report with a device state and
timestamp. The Windows command journal/poller core now models durable dispatch
and refuses replay after a persisted `dispatching` state. The Windows `run`
worker now loads the existing ATM credential file, polls Central, and attaches
one serialized ITL adapter/status poller when exactly one device is connected.
Product physical acceptance is off by default. Only the explicit
`KALASH_PRODUCT_CASH_ENABLE=OWNER_ATTENDED_PRODUCT_CASH` configuration selects
the product owner; it does not replace Central cash enablement, signed consent,
device preflight or owner attendance. The default worker never enables cash.
For the specifically authorized one-note test, `run --one-100` restricts routing
and decisions to one INR100, including in-flight notes, and automatically stops
at that capacity. It naturally exits only after clean closure, exact Outbox ACKs
and reverified DISABLED/empty escrow with unchanged final inventory/counters.
Regular `run` stays resident. A readback-derived authenticated heartbeat runs
every five seconds without a second event reader; shutdown reports unavailable.
The Central client sends the configured HTTPS authority as `Origin` on all
requests. A durable, truthful unavailable-health POST must succeed before the
REST child starts. HTTP failures report status only, not response bodies.
Observed `DeviceStatusResponse.stateAsString` initialization states are parsed
explicitly; unknown states still fail closed. Startup-only recovery preserves
original raw/state evidence and is restricted to cash-free initialization with
current DISABLED/empty/profile/inventory/counter and disconnection proof.

The observed firmware waits in `IDLE` after EnableAcceptor; `ACCEPTING` refers
to note transport, not waiting for insertion. Report the actual `IDLE`, never a
fabricated `ACCEPTING`. Central accepts it only with
`itl-idle-after-enable-v1`: matching command/session/device, durably ordered
disabled observation -> Enable dispatch/ack -> later owned-reader IDLE,
numeric device state 5, manual escrow, verified routes/health/empty escrow, and
identical baseline/current six-level inventory and four counters. Bare IDLE,
stale/mismatched proof or a later changed intake baseline is rejected.
Controller observation times retain strict local ordering. Their comparison to
Central's command creation permits only the existing five-second command clock
tolerance; a server/client clock difference must not reverse local causal order.
The signed expiry and recent observation checks are unchanged.

The explicit `scripts/reconcile-failed-cash-start.mjs` operator tool defaults
to dry-run. `--apply` only closes the specific failed-start zero-note shape
after matching archived state/raw/command proof and fresh physical evidence.
It preserves the original unknown command, ledger and stream; it never creates
a donation/mint, resets event sequence or re-enables cash. It is not a general
reconciliation override for unknown cash.

The product owner is the sole consuming ITL reader and physical action sender.
It persists note identity/accept decision/dispatch intent and events before
escrow actions, uses the existing command journal to forbid physical replay,
and replays only durable Outbox envelopes after restart. Unknown dispatch and
the non-atomic raw-event consumption/persistence window fail closed for
operator reconciliation rather than reconstructing notes from inventory.
An exclusive, atomically replaced `state.json` contains note state, dispatch
markers and the ordered Outbox; `raw.jsonl` and persisted poll-in-flight markers
detect raw consume/commit gaps. An active restart locks reconciliation and never
replays a physical operation. Only the exact acknowledged Outbox head retires.

`GET /api/controller/:atmId/cash-session` returns the active bound session and
durable close request. `POST /api/controller/:atmId/cash-events` accepts the
strict `streamId, sequence, deviceEventId, occurredAt, visitId, cashSessionId,
type, data` envelope in `src/cash.ts`. Sequence persists across sessions and
restarts, begins at 1, and advances exactly once. `deviceEventId` is
`streamId:sequence`. An identical duplicate receives the same ACK only after
DB processing; gaps, changed payloads, new-stream resets and conflicting note
keys reject and lock. The Controller ACKs only the exact stream and sequence.

Central stores `cashSessions/{cashSessionId}`, per-ATM
`cashEvents/{streamId}:{sequence}`, `cashStreams/{streamId}` and rejected
payload evidence. `cashBudgets/demo` counts cumulative stored/pending paise
and notes independently of session limits. Limits remain INR 400/session
(including in-flight accepts), INR 1,000 and 10 notes for the demo.

Paired-screen `POST /api/atm/:atmId/visits/:visitId/done` and owner
`POST /api/visits/:visitId/cash-done` only persist stop requests. The same
device loop keeps observing late STORED while disabling. Closing requires
explicit disabled/empty escrow, six unique INR denomination levels, all four
stored/stacked/dispensed/transferredToStack counters and matching Central totals.
Timeout alone is never success. Reasons precede the closing event; unresolved
or conflicting evidence preserves `needs_reconciliation` and the ATM lock.
Zero closes without donation/mint. Valid nonzero closing atomically creates
the deterministic cash donation, wallet/temple totals and the existing mint job.
The net/fee fields are equivalent accounting units, not transferred funds.
Confirmed cash remains visible until the paired screen uses Finish (`/close`).
Browsers show INR, a finite deadline and Done; a local stop request suppresses
acceptance instructions even if its HTTP response is lost.

`node scripts/verify-cash-session.mjs --preflight atm-01` reads registration,
reconciliation lock and global demo reservations without granting cash permission.
For an actual UUID, `node scripts/verify-cash-session.mjs CASH_SESSION_UUID`
replays persisted event evidence, checks attribution and exact owner/temple points,
then verifies persisted mint completion against the canonical receipt and exact
Stamp/ERC1155 events. Pending, missing, changed or contradictory evidence remains
nonzero. This is read-only DB/chain proof, not independent physical note proof.

The separate `diagnose-cash` command reuses that ITL adapter and has no Central,
donation, or mint side effects. It requires interactive owner/operator
confirmation, enables only ₹100, observes `ACCEPTING`, accepts at most one
matching ₹100 INR ESCROW/STORED event, requires Done, then reconciles payout
levels and stored/stacked counters. Device state/events are durably journaled
before delivery to the consumer. The live hardware acceptance-state spelling
and diagnostic workflow have not yet been verified on the device.

After cash confirmation, reserve onsite mint and permit only that donation's
optional ATM photo. Finish/Skip/inactivity stops camera tracks, discards unposted
preview, clears identity and revokes photo authority. Published photos remain.
Successful mints refresh Collection silently; pending mints do not increase counts.
### M5a API and rollout gate

The M5a slice implements crypto visits and receipt verification while Cash
remains disabled. Responses explicitly state the Cash availability/reason and
do not accept Cash visits. The phone creates a donation only after an authenticated
explicit claim. No cash command, simulated device readiness or synthetic donation
confirmation may be created.

- `POST /api/controller/:atmId/pairing`: ATM-bound Controller bearer -> 120-second,
  single-use pairing code. Only a SHA-256 digest is stored.
- `POST /api/atm/:atmId/pair`: exchange code for an 8-hour `HttpOnly; SameSite=Strict`
  cookie, scoped to this ATM API path; `Secure` on HTTPS. Replacement invalidates
  the old screen and preserves the active reception.
- `GET /api/atm/:atmId`, `POST .../visits` (`mode=crypto`, stable `requestId`),
  `POST .../visits/:reference/close`: screen-authorized state/create/close.
  Atomic ATM pointer and request record enforce one reception and no duplicate
  creation. Close is forbidden if a cash command is attached.
- `GET /api/visits/:reference?templeId=...`: public context only, no owner wallet,
  signatures or device credentials. `/mine` additionally requires wallet identity.
- `POST /api/visits/:reference/claim`: authenticated wallet + explicit Join
  consent; transactionally claim once.
- `POST /api/visits/:reference/donation`: only the claimed wallet can create the
  single, idempotent kind=1 intent for this visit. Central receipt verification
  remains the only path to confirmation and mint.
- `POST /api/controller/:atmId/health`: authenticated, ordered read-only heartbeat
  from the registered Windows Controller, including USB/device/router status.
  Stale/missing or disconnected state disables Cash; it never disables Crypto.
  Controller must not call consuming event-poll endpoints for this health report.
  Report every 10 seconds or less; status older than 15 seconds is offline.

The follow-up M3 cash goal extends this contract with the already specified
one-use cash-consent signature, Controller Ready, finite acceptance, ordered
STORED events, inventory reconciliation, stamp and optional ATM photo. No
CashDevice command is enabled by M5a.

Until a fresh authenticated readiness report is received, Central reports
hardware as offline/unknown and the ATM remains Crypto-only. The health path
does not authorize or execute ITL operations.

### M3 local REST API process boundary

The KALASH-owned .NET 10 Controller is kept under `CashMachine/CashMachineController`.
The manufacturer CashDevice REST API Server is a non-redistributable local
driver under the separately ignored `CashMachine/RESTAPIServer` area. Git tracks
its README only, never the server, vendor logs, credentials, or configuration.

The user-supplied manual extract identifies CashDevice REST API v2.0.0 on .NET
8.0 and requires `serverconfig.json` to bind `localhost:5000`; package metadata
confirms the .NET 8 runtime target and the local server configuration. The
included `appsettings.json` has a wildcard `AllowedHosts` and a packaged signing
setting, so the unmodified package must not be launched. The Controller must
override `AllowedHosts` to `localhost;127.0.0.1;[::1]` and provide `Jwt__Key`
from protected local configuration in the child environment. Never log or
commit that value, or modify the vendor distribution to make the override.

The supplied Manual v14 extract (p.182) says request `Route=1` means RECYCLER
for Spectral Payout. The SDK v2 Postman `Route=3` example is for NV4000;
`acceptRoute=7` is a readback representation, not a request value. Use `1` only
for the confirmed Spectral Payout configuration and verify its readback for the
actual firmware/dataset; do not generalize. `GetDeviceStatus` consumes events,
so no additional poller may be introduced.

The host must use an explicit local server directory, refuse an already-used
port instead of attaching to or stopping its owner, and retain only the process
handle for the child it starts. Drain but do not record vendor stdout/stderr;
vendor logs can contain credentials or tokens. Do not force-stop the child while
device state is active or unknown. M3 host tests use a fake child. M5a includes
no cash operation or service registration. M3 Stage 1 and disabled Stage 2
initialization have now been run against the authorized local installation;
see TASKS for evidence.

The current host source is the package-free
`CashMachine/CashMachineController/KALASH.CashMachineController.csproj`.
`run` is explicit; build and tests do not start the vendor server. Configuration
requires the dedicated server directory and an absolute `dotnet.exe` path. If
no signing key is supplied, the Controller creates a fresh ephemeral key in
memory. The child does not resolve its runtime through the parent `PATH`; it
receives only platform environment variables plus the exact `AllowedHosts` and
`Jwt__Key` overrides. Startup checks that the process remains alive; API
authentication and device readiness are separate checks and are never inferred
from an open port.

`ItlControllerClient` targets only `127.0.0.1:5000`, keeps credentials and bearer
tokens in memory, refreshes the token before expiry, and serializes each request.
`ItlControllerClient` exposes authentication, USB/device/inventory GETs and
specifically gated initialization, acceptor and manual escrow methods. The
product execution owner serializes those operations; tests/builds never start
hardware. Credential updates and product payouts are not part of M3 intake.
HTTP errors expose status codes, not response bodies; there are no blind retries.

The Stage 1 `inspect` command loads the default v2 Authenticate sample from the
local Fresh SDK Postman collection in memory. Before starting, it compares the
dedicated server's `users.json`, server DLL, runtime configuration, server
configuration, and appsettings to the Fresh package. Any mismatch fails closed;
it never initializes or rewrites users. It then verifies loopback-only listener
addresses and Host filtering, authenticates, reads `GetConnectedUSBDevices` and
`GetAllCashDevices`, and stops only its own child. Passwords and tokens are
never printed or persisted. The local one-command entry point is
`CashMachine/CashMachineController/Inspect-Local.ps1`.

`Initialize-Local.ps1` is the separate Stage 2 hardware initialization. It uses
one `OpenConnection` with a single detected COM port, the Spectral Payout route,
and `EnableAcceptor=false` / `EnableAutoAcceptEscrow=false`. A sole poller
consumes `GetDeviceStatus` until all route-result events succeed and state is
`DISABLED`; it then verifies model/firmware/dataset, empty escrow, denomination
levels, counters and currency assignment. Only with a verified disabled and
empty state does it issue one `DisconnectDevice`, verify the connected-device
list is empty, and stop its child. An ambiguous OpenConnection or unresolved
device state leaves the owned server child running with its PID reported; do
not retry or kill it until reconciled. This sequence issues no cash acceptance
or payout commands.

`Reconcile-Local.ps1 -ServerPid <pid>` attaches to only that PID after verifying
it runs the dedicated REST DLL and exclusively owns port 5000. Reconciliation
performs GETs and one consuming `GetDeviceStatus` poll only. The separate
`Complete-Initialization-Local.ps1 -ServerPid <pid>` requires a safe numeric
device identity, disabled state, empty escrow, successful inventory reads, and
an empty connected-device list after its single `DisconnectDevice`; only then
does it stop that exact child PID.

The vendor child receives `AllowedHosts=localhost;127.0.0.1;[::1]`, a per-run
ephemeral JWT key, and warning-level application/Serilog filters. Its stdout
and stderr are drained but not recorded. Vendor file logs are not read or
committed. Service/autostart and persistent JWT decisions are deferred.

Canonical link generation is shared in `src/atm.ts`; local HTTP API tests return
an explicit QR-unavailable reason instead of manufacturing a mobile link.
`scripts/bootstrap-atm.mjs` provisions the registered ATM without overwriting an
existing credential; `scripts/pair-atm.mjs` saves its short-lived pairing code
only in the Controller's protected local secrets directory. Neither logs secrets.
Registry release verification prints bounded progress and identifies the package
on network failure. QR uses the already-locked qrcode 1.5.3 as a direct dependency,
with types 1.5.5; all release evidence is regenerated before executing dependencies.

The canonical regional URL is used for Firebase/Reown/metadata/API origin checks.
Cloud Run's generated status.url alias is not a second application origin.
Actual runtime SA/custom-token signing, private DB writes and idle mint have been
verified on the deployed image; source commit is returned by `/api/health`.
Wallet diagnostics expose at most100 sanitized entries in
